# Litha speed and coding reliability: source audit

Reviewed 2026-10-28 on `codex/litha-speed-quality-20261028`. This is a source review and a measurement proposal. No engine, credentials, provider requests, model inference, server settings, evaluation fixtures, or owner files were used. Sources below were opened directly; upstream `master` documentation is moving and does not establish the installed engine's revision or supported options.

## Repair incomplete replies before tuning speed

At branch base `79489ad`, `launcher/litha.py:ask_stream` requested at most 700 output tokens but used `bool(finish_reason)` as successful completion. Consequently `length`, unsupported tool completion, and arbitrary nonempty strings could admit partial code as a completed answer. Receiving text establishes neither completion nor correctness.

The upstream [llama.cpp response implementation](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/server-task.cpp) assigns `length` to limited generations and `stop` to normal EOS/stop-word completion; tool calls have a separate reason. Its [server benchmark](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/bench/README.md) explicitly counts `length` as truncation. This supports a compatible client repair without changing models, sampling, prompts, or token limits:

- Accept `stop` as the normal text terminal. Close immediately rather than awaiting another read for an optional usage chunk.
- Report a static, useful incomplete-code warning for `length`; unsupported completion reasons and unknown reasons must also fail visibly. A later `[DONE]` cannot convert an earlier error into success.
- Preserve the existing `[DONE]`-only compatibility path explicitly. It is a transport terminal convention, not independent evidence that code is complete.
- Preserve streamed partial text for visibility, but do not commit it as a successful assistant-history turn. The candidate uses typed `LithaIncomplete` for the limit case; the session emits one `incomplete` terminal and the UI retains partial text plus a warning, marking it excluded from future assistant history. A validated delta accompanying `length` is yielded before the typed terminal so the final chunk is retained. No automatic continuation request: that would introduce more inference, cost, cancellation states, and possible duplicated code.

Root's candidate implements these backend/session changes. Independent injected-response probes rejected `length`, `content_filter`, `tool_calls`, and an arbitrary reason, including when followed by `[DONE]`; all response objects closed. Independently reran seven new completion groups, 14 retained protocol groups, nine session groups, 12 app-hook groups, nine context groups, two context-wire groups, and six existing toggle tests: all passed. The actual-session completion check uses a real worker thread with a fake stream and establishes chunk then one incomplete terminal, including an only/final chunk carrying `length`. These checks used synthetic responses/source and no sockets. UI behavior is separately tested; this note does not claim generated code was executed or verified.

## Transport scope and follow-up

The current parser consumes one JSON payload per `data:` line. It handles the server's common line format, comments, usage-only chunks, and cooperative cancellation boundaries. It is not a full general-purpose SSE decoder. The [WHATWG event-stream specification](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream) dispatches on blank lines, joins multiple data fields with newlines, permits a leading BOM and several line endings, and discards an unfinished event at EOF.

The final candidate validates both raw stream UTF-8 and the decoded JSON content string before yielding it. JSON-escaped lone high/low surrogates can otherwise bypass wire-byte validation. Independently reran the seven completion and 14 protocol groups after this correction: malformed raw bytes and escaped lone surrogates fail statically and close the response; valid Unicode and literal code containing the characters `\\ud800` remain intact. This is protocol correctness, not validation that generated source is safe or correct.

A separate bounded decoder could retain pending event bytes, dispatch assembled payloads, cap event size, and reject malformed UTF-8/JSON with static errors. Test multiline JSON events, BOM, CRLF, comments, fragmented reads, oversize events, and EOF without dispatch. Existing one-line synthetic fixtures are not proof of full SSE compliance; compatibility needs deliberate tests rather than silently changing their meaning. No reconnect/retry should replay authenticated generation automatically. Cooperative cancellation still cannot interrupt an already blocked read or guarantee GPU work has stopped.

## What `cache_prompt` does

Litha already sends `cache_prompt: true`. The current [llama.cpp server documentation](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md) describes reuse of a common token prefix in KV cache, processing the differing suffix when possible. It is not semantic answer caching. Reuse depends on server/backend state and request similarity; the documentation warns that changing batching through caching can change logits. The chat endpoint accepts completion-specific options, but support on an installed or alternative engine must be checked, not inferred from current upstream docs.

Keep stable system text and history serialization. Do not move untrusted source into the system message or add hidden long-lived source memory for cache hits. Current selected code follows the changing user question, so that portion need not share a prefix across questions. Reordering it might increase reuse but changes model input and needs separate quality evidence. The candidate's compact JSON removes formatting whitespace while preserving parsed file names, numbered source lines, and escaping. The synthetic context-wire verifier measured request-byte reductions from 0.79% to 39.35% in its four cases; these are not measured token savings or a measured latency improvement. Each comparison asserts that its previous-format capsule fits the existing 65,536-character limit; the 800-lines-times-three sample replaces an earlier oversized, invalid baseline comparison. Cache benefit must be observed, not assumed from the request field.

The outer request envelope now also uses compact UTF-8 JSON. [RFC 8259 section 8.1](https://www.rfc-editor.org/rfc/rfc8259.html#section-8.1) specifies UTF-8 for exchanged JSON. This preserves the decoded request values; malformed Unicode fails with a static error before reading the key. This representation change does not alter the system prompt, chosen model, sampling parameters, output budget, cache option, or thinking-template option.

## Context and quality

[Anthropic's context-engineering article](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents) recommends curating a small, relevant set of context and separating deliberate retrieval/compaction choices. This is engineering guidance, not a coding-quality result for Litha's local model. Preserve explicit owner file selection, source boundaries, line citations, and attachment limits. Compact representation can preserve all selected source; model-generated summaries would risk deleting the exact line needed to diagnose a bug.

The [Lost in the Middle paper](https://arxiv.org/html/2307.03172v3) reports position-sensitive performance in multi-document question answering and key-value retrieval. Those tasks and tested models do not establish Litha's coding accuracy. A practical inference is to test relevant-file and line placement rather than assuming a larger context improves answers. No paper here warrants a new quality score or an activation decision.

## Bounded measurement plan, not executed

First finish offline protocol checks: every stop reason, invalid UTF-8, terminal-stop-with-blocked-next-read, missing terminal, cancellation, response closure, and source-capsule preservation. Use fake monotonic clocks where useful; fake throughput is not native model throughput.

For a later explicitly authorized local-engine experiment, record model/GGUF hash, engine build, GPU/driver, context size, sampling, output budget, prompt bytes/tokens, and competing load. Keep requests and outputs synthetic and free of credentials/private project code. Measure request-to-first-content, request-to-terminal, output token count, cancellation-to-worker-release, and truncation/error counts separately. Report cold startup separately from warm inference. Use repeated paired cases with the same source and question, changed questions with a stable prefix, and changed source; alternate ordering to reduce warmup bias. Report sample count and median/p95 with failures included, without treating warm cached requests as cold performance.

Where the installed server returns them, distinguish client elapsed time from its prompt-processing, generated-token, and cached-token metrics. The server benchmark's truncation count is useful alongside latency; a fast partial answer is a failure. Judge coding results on predeclared, independent tasks for valid syntax, intended behavior, correct file/line references, and honest test claims. Keep any new benchmark artifacts outside harness-owned baselines, and do not claim evaluation admission, release readiness, or quality improvement until the responsible gate actually runs.
