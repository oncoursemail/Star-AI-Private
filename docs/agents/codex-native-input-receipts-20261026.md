# Native input delivery receipts

The Windows desktop and gameplay sinks previously discarded `SendInput`'s return count. A rejected call could increment the actuator's completed-call counter and let Home report success. Both sinks now require exactly one accepted event for each one-event request. Zero, an unexpected count, or an operating-system error raises a static `InputDeliveryError`; no failed action is automatically replayed. Gameplay cursor placement also checks `SetCursorPos`'s result.

The actuator stops accepting plans after delivery failure, discards queued events, and retains failure and held-input state for the session report. Cleanup attempts every owned key/button release even when another release fails. A confirmed rejected down is never treated as owned. A successful or unknown down can receive a best-effort UP through a cleanup-only method after focus changes; ordinary down, movement and typing retain their foreground guards. Unicode input stops at a failed pair without replaying the character or remaining text. Hands releases modifiers and timed-plan inputs on failure, STOP or interruption, and failed actions have an error log rather than a done log.

`GameSession.report()` separates attempted/completed sink calls from native accepted/failed events. Recorder sinks retain their existing None-return API and report unavailable native receipts as None. Home's registered game activities stop stepping after an actuator failure, retain the receipts, and force delivery/release failures to `verified=False`. Threads are tracked before startup, including interrupted startup. Cleanup cannot claim completion or race a release against an unjoined worker. An uncertain unstarted/current-thread join stays pending instead of assuming native work ended; a genuinely unstarted worker may therefore require process restart. Per-event lag includes time consumed by earlier calls in the same due batch; profiles and intentional timing delays are unchanged.

Verification uses fake native APIs only: `python scripts/verify_native_input_receipts.py` passes 30 retained cases, including zero/invalid/unknown native replies, partial Unicode/text, foreground changes, STOP inside a due batch, modifier/drag cleanup, failed cleanup, no replay, lag accounting, recorder compatibility, stalled workers, action logs, and actual registered game activity propagation. One case launches a real Python thread with a blocked fake native DOWN, interrupts startup, and confirms that UP waits for DOWN to finish and the worker to end. The existing play/computer/Home subset passes 119 tests; the retained autonomy recovery verifier passes 31 cases. Ruff passes; focused Pyright for actuator/session/new verifier is clean. Harness tests and evaluation files are unchanged.

No native desktop action or remote benchmark was performed for this patch. An accepted Windows input count confirms insertion into the input stream, not that the target app achieved the intended result. App-level verification remains necessary. Windows blocking can also reject a cleanup UP; such outcomes remain failed/unverified rather than claiming guaranteed release or perfect control.

Primary reference: [Microsoft SendInput documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput). It defines the inserted-event return count and notes that UIPI blocking is not identifiable from the return value or `GetLastError` alone.
