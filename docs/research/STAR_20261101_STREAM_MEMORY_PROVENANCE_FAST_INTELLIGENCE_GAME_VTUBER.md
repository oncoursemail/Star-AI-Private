# STAR AI: Scene-grounded memory, faster intelligence, autonomous gaming and convincing VTuber streaming
**Research and implemented correction:** November 1, 2026, US Central (November 2 UTC).
**Base:** Draft PR #891, scene-handoff work. **Scope:** offline, owner-approved, no game input, broadcast, training or deployment.

## 1. Audited defect: an authentic old-game memory can become a false new-game reaction

Star already had verified practice episodes, signed continuity journals, a stream stage, and a host-bound game-scene transition. It could reject an old-game **event**, yet a host might have generated an owner-approved **memory packet** before switching games, and then supplied that packet after the switch. The stage appended its content to a new-game speech prompt without checking its source game.

**Reproduction on the pre-change branch:** bind StarStage to game B, submit an appropriate moderated viewer question, then pass EpisodePacket/ContinuityPacket created for game A. Both old-game records appeared verbatim in the planned response context. Even when the packet's previous approval was legitimate, the current response would be misleading. This is not evidence of a malicious host or proven broadcast leak, but it is a concrete cross-scene context-integrity defect.

### Implemented
- Both public episode and continuity packet types now contain a game-scope identity, generated by their respective verified producer. The digest is over game, version, objective and situation, separated by NUL; it is not a secret or an authorization signature. Continuity and the live episode producer use identical inputs and format.
- StarStage consults the StreamDirector's **current** host-bound game scope, not merely a potentially stale caller-supplied game label. Optional independent host labels must not contradict the bound scene. A mismatched or unscoped memory packet is withheld from a scene-bound turn, while normal verified event/chat arbitration proceeds.
- Explicitly transitioning to no game blocks game memory packets from accidental injection. Historical memory is not erased; a separate owner-curated cross-game retrospective query can be developed later.
- Legacy unbound callers retain the existing behavior; **production must call** `transition_game()` when entering/leaving a scene. Packet provenance alone does not authenticate an untrusted caller.
- A bounded `off_game_memory` aggregate counter helps show suppressed stale context without revealing memory contents. KnowledgeStore packets remain independent source-approved knowledge; they do not claim to be memories of play.

### Acceptance evidence
- Before correction, game-A episode and continuity data were both attached to game-B chat.
- After correction, tests cover game-A episode suppression, historical continuity suppression, same-game acceptance, stale independent host scope, missing metadata, a director-bound scene without an explicit per-call scope, and exiting to a no-game scene.
- Existing unit tests assert actual signed-practice episode and sealed continuity packet metadata agree on full scope, while a changed situation produces a different scope.
- No frame rate, synthesized voice naturalness, gameplay success or inference token rate is improved merely by this change. This fix protects **truthful conversation** and avoids irrelevant prompt baggage, not GPU computational speed.

## 2. Real-time cognition: treat action timeliness as intelligence

Two late-2026 papers provide complementary evidence that model reasoning quality cannot be judged without wall-clock time.

**RealtimeBench / TORSI**, submitted **October 14, 2026** (Pan et al.), tests 180 live-clock game tasks. Its two-timescale teacher/student method improved the reported fast-agent mean score from 13.51 to 24.19 after two learning rounds. The result is external research, **not a Star result**, and should not justify live activation without independent paired trials. <https://arxiv.org/abs/2610.20665>

A separate **Realtime-Bench** Stanford Digital Economy Lab working paper dated **October 22, 2026** distinguishes Wall Clock, Paused Clock and Token Clock. Its reported best Wall Clock success rate was 44%, highlighting the limits of even powerful slow agents under ongoing gameplay. <https://digitaleconomy.stanford.edu/publication/realtime-bench-can-frontier-models-solve-real-time-interactive-problems/>

**Architecture to build and benchmark, not yet implemented here:**

1. **Fast reactive controller**: 10-30 Hz game-state tracking from host-verified events and small observation crops. Only dispatch preapproved, bounded symbolic actions; validate scene age and focus at the physical input boundary. When the clock budget is exceeded, deliberately **skip** an action rather than acting on a stale frame.
2. **Tactical controller**: about 1-3 Hz for inventory, objective selection, map state, party coordination and short-horizon plans. It can amend strategies for the fast controller but cannot press keys bypassing the action gate.
3. **Offline teacher**: between trials or with the game demonstrably paused, examine failures, propose mechanic hypotheses, generate challenge ladders and candidate skill cards. No teacher calls are admitted during time-critical gameplay or under stream/GPU pressure.
4. **Promotion**: preregister *unseen* maps, game versions and seeds. Compare baseline and candidate in equal wall-clock conditions, with opponent/player variation and paired seed design. Require stable transfer gains, bounded p95 action delay, no severe per-scenario regression, and clean source provenance. An improvement in a simulator or a particular map is not evidence of generalized mastery.

Already-existing local components include `game_realtime_loop.py`, `game_deadline_router.py`, `game_skill_gate.py`, `game_paired_study.py`, `gameplay_skill_bank.py`, and `stream_load_governor.py`. **Integration gaps:** a real owner-approved game adapter, continuous perception with frame identity, and multiple truly independent live-game measurement runs. Do not duplicate these modules simply to create more features.

## 3. Fast local inference: optimize the complete stream, not token benchmarks alone

The user's previous Windows snapshots showed an RTX 3060 Ti 8 GB experiencing both very low free VRAM and, in a later separate reading, substantial headroom. That variance rules out selecting a permanent configuration using one GPU snapshot. An inference server can allocate large VRAM while momentary GPU utilization is near zero. Game rendering, OBS rendering/encoding, avatar physics, vision and LLMs contend for resources in different ways.

**Controlled experiment matrix** (all choices are provisional and hardware/version-dependent):
- Keep a small responsive real-time model on the CPU or secondary machine when the main GPU is constrained; reserve a stronger model for between-turn planning.
- Test 4/6/8-bit quantization and different GPU-offload layer counts against **first audible response**, quality and game frame pacing, not just raw tokens/second.
- Keep reusable system and approved project context at a stable beginning of prompt; attach only source-relevant facts. Maintain separate caches for sensitive sessions and enforce cache eviction and session isolation.
- Benchmark llama.cpp speculative decoding modes (draft model, n-gram, MTP/EAGLE3 if compatible), real prompt lengths and varying concurrency. The project's SPEED-Bench client reports draft acceptance, latency and throughput, but it cannot establish speech quality or game win rate: <https://github.com/ggml-org/llama.cpp/blob/master/tools/server/bench/speed-bench/README.md>
- Test unified-KV / slot-caching configurations empirically. A **October 2026** llama.cpp issue describes `--cache-idle-slots` saves stalling concurrent streams under interleaved KV for seconds; do not blindly assume more cache or more slots means lower p95 latency: <https://github.com/ggml-org/llama.cpp/issues/30252>
- Prefer bounded CPU/RAM prefetch, incremental summaries, limited concurrent background work and admission controlled by actual OBS/game pressure. Any cache changes must preserve privacy boundaries; do not reuse viewer-private context between unrelated chats.

**Measurement protocol:** same game, map, OBS scene, avatar, audio pipeline, resolution, cap, inference workload and prompt corpus; baseline versus candidate alternating order with warmups; record game-presented p95/p99 frame time, OBS render/encoder skipped-frame deltas, first-*audible* syllable p50/p95, speech-to-expression skew, available GPU memory minima and complete response quality. Reject a candidate if a nominal token throughput win creates gameplay stutter, stale speech, or incorrect facts. A test must include idle, normal gameplay, voice activity, heavy scenes and game transitions.

**Rust and CPU acceleration:** Rust is valuable for the low-jitter capture/input bridge and reproducible telemetry transport once profiling identifies hot functions. Rewriting the Python planner in Rust without measured CPU or scheduling bottlenecks is not a guarantee of better model speed. For local 8 GB GPUs, memory placement and model architecture often dominate.

## 4. Humanlike VTuber behavior = continuity, grounded reactions and good timing

Star can be an expressive fictional VTuber with a consistent personality, recognizable habits and hobbies, cat/puppy modes, friends and character lore without impersonating a human or fabricating actual lived experiences. The most important improvement is *coherent causality*: an action happens, it is observed, the speech refers to that event, and the face/voice respond at the moment the audio is heard.

**Runtime signal path:** game capture / host telemetry -> scoped observed event -> moderated turn arbitration -> short response plan -> speech generation -> **actual playback-start confirmation** -> mouth/gaze/expression samples -> playback-end confirmation -> verified episode summary. The queueing of TTS is not proof that a word was heard. When the game changes or the owner interrupts, revoke old plans and physically stop/flush audio before accepting a new-scene utterance; otherwise an old sound can survive the new label.

**Voice improvements for a controlled trial:** a local VAD plus conversational end-of-turn detection, an optional low-overhead CPU voice model, prosody control tied to observable outcomes, varied short reactions instead of repeated catchphrases, natural silences, and strict handling of owner interrupts. LiveKit's current documentation specifies that `v1-mini` can run locally on CPU and that it requires proper agent/VAD integration; evaluate it against the project's existing deterministic `stream_turntaking.py` before adopting it. <https://docs.livekit.io/agents/logic/turns/turn-detector/>

**Avatar behavior:** gaze should originate from trusted verified scene targets, with eased eye motion, blinks, small attention shifts, mouth shapes keyed to **played PCM**, expressive brows and nonintrusive idle breathing. An anxious or delighted expression must not be derived merely from a viewer's claim of victory. VTube Studio's plugin API can inject custom tracking parameters and requires local user permission; do not bypass authorization or give arbitrary chat command authority over the avatar. <https://github.com/DenchiSoft/VTubeStudio/wiki/Plugins>

**OBS:** prefer its authenticated WebSocket 5.x read-only `GetStats`, `GetStreamStatus` and `GetRecordStatus` for a **nonbroadcast** acceptance rehearsal. Render-skipped frames and output-skipped frames are distinct metrics, and lifetime totals must be compared over valid same-session intervals. Avoid any output-start commands in a rehearsal. Official API: <https://github.com/obsproject/obs-websocket/blob/master/docs/generated/protocol.md>

**Memory and social behavior:** allow Star to answer questions about a real attempt (such as failing a jump and later succeeding) only from independently signed practice records and scope-bound continuity. Provide explicit owner review of what may be mentioned publicly. Separate character lore from evidence-backed experiences and never invent achievements, private conversations, or social relationships. Avoid impersonating a viewer; treat chat text as untrusted input.

## 5. Game creator and general-knowledge engineering: quality must be observable

Star's Roblox/Blender/Minecraft creation objectives need a **generate -> inspect -> execute -> compare -> repair** cycle:
- Use source-grounded Roblox API lookups and version-pinned Luau linters, plus static checks for scripts, assets and forbidden tool access.
- Verify 3D object transforms, supporting surfaces, scale, pivot orientation, UV/material boundaries, clipping, path connectivity, physics/collisions and lighting under multiple camera views. Don't use a text-only model's “looks good” claim as visual proof.
- Roblox's official Studio testing modes support server plus up to eight simulated clients; StudioTestService and VirtualInput support programmatic join/leave and UI actions, subject to the current Studio environment. This is a credible native game-QA path: <https://github.com/Roblox/creator-docs/blob/main/content/en-us/studio/testing-modes.md>
- Use short game-design tasks with independently graded player success, resource gathering, team mechanics, network conditions and usability as a curriculum. Harder tasks should only unlock when recent unseen tasks pass.
- For general knowledge, retrieve **date-stamped, source-linked, topic-relevant** facts; require corroboration for consequential claims and a short “I don't know” fallback. This is source grounding, not parameter-weight training. Keep project/IP/customer secrets outside streaming prompts.

Cross-domain quality matrix already exists (`stream_workload_quality_matrix.py`): game commentary, general knowledge, Roblox creation and dialogue should all pass separate witnessed tests before recommending a speed change. Prevent aggregate scores from hiding regressions on one domain.

## 6. Prioritized engineering milestones

**P0 — Apply now (this change):** avoid wrong-game memories with packet producer scope, consumer checks and regression tests. No new permissions, processes, background work, broadcasts, mic capture or live game input are enabled.

**P1 — Integration, higher value than another hypothetical model upgrade:** link the real Windows game-switch observer to `StarStage.transition_game`, flush real playback with confirmation, and supply scope-matched `StreamEpisode.public_packet` / `StreamContinuityVault.public_packet` only on separately approved viewer questions. Run crash/restart, rapid game-switch, overlapping voice, wrong-scope host signal, and no-game tests.

**P2 — Real nonbroadcast rehearsal:** simultaneously run approved test game, TTS, avatar and OBS read-only stats under constrained GPU headroom. Verify input to output latency, actual render FPS, microphone/audio echo isolation, scene handoffs, VRAM and no stale game callouts. Keep broadcasting disabled.

**P3 — Intelligence performance trials:** preregister unfamiliar maps, paired seed/player/opponent trials, A/B model configurations and scenario-specific tail latency. Use actual signed success/failure and visual QA, not subjective “smarter” impressions.

**P4 — Stream personality and creative autonomy:** independent graded game practice, player-friendly tutorials, spectator moderation, persistent approved hobby/memory journal, real-time expressive voice/eyes/hair, and verified game-building agent. Anything involving external contact, money, secrets or irreversible operations continues to require an appropriate authority boundary.

### Operational caveats
Research may be outdated as upstream tools evolve; pin exact versions before implementation. This module-only correction does **not** give Star real eyes, a mic, any newly trained model, game-playing ability, consciousness, or human identity. It makes one existing source-to-speech boundary more reliable so those future integrations can be evaluated without a known false-memory defect.
