# STAR AI — verified gameplay-to-stream learning and viewer fairness
_Research and implementation review, 2026-10-30. Draft only; no services, games or OBS streams enabled._

## Measured state, not wishful capability

STAR already contains distinct components for CPU/GPU inference admission (`stream_qos.py`, `stream_brain_governor.py`), focus-aware moderated chat (`stream_focus_inbox.py`), physical-audio progress and output-callback metrics, signed gameplay trials (`gameplay_skill_bank.py`), replay/transfer evaluations and Roblox Studio automation. Building more independent components will not establish that STAR can play an unknown game, build a releasable one, or converse naturally. The high-return next step is *closing the evidence loop* across those existing components, with offline and physical playback acceptance.

This PR fixes a concrete fairness weakness in deferred viewer questions: the inbox used `signal_id` as a fallback when `speaker_id` was absent. Since event IDs differ per message, an anonymous sender could defeat the intended one-question-per-speaker limit while the game was intense. The amended opt-in inbox **declines** questions without a nonblank, stable chat-host-supplied speaker ID, then pseudonymizes the ID immediately with session-keyed HMAC. Raw IDs are never exposed to the StreamDirector or metrics. The ID must be attested by a trusted moderated chat host, not generated by the LLM or taken from an editable display nickname. This does not add authentication, moderation, or new speaking authority. The original physical microphone/stream mute, owner opt-in and silence defaults remain necessary.

## Findings from current research

### 1. A gameplay skill must transfer into a **different episode**, not just be remembered

**MemoryArena** (February 18, 2026) studies interdependent multi-session tasks and reports that strong long-text recall need not translate to successful memory-guided action. STAR should therefore score whether her stored prior *verified* attempts improve the next session's decisions. For each playable lesson, save a compact skill card: game/engine version; objective; controllable action family; observation predicates; preconditions; host-attested outcome; evidence digest; practice-only source; last revalidation date. The model may consult the card for an unfamiliar challenge, but no practice result can alter or inspect independent held-out validation.

**AI for Games in the Foundation Model Era** (September 15, 2026) emphasizes that playing, modeling, designing, building, adapting and testing are distinct but potentially transferable roles, and that evidence must be reestablished in each target game. A verified `jump_timing` practice skill may inspire a new parkour mechanic; it is **not** proof that a generated Roblox obstacle is playable. STAR should feed a learned *hypothesis* into Studio, then verify collisions, start/finish, respawn, win conditions and saved state in that actual engine. Transfer retains provenance and can be revoked after game updates.

### 2. Split inference by urgency and account for batching contention

llama.cpp's current **server developer documentation** explains that active slots share a batch and that `llama_decode` is the critical server-thread bottleneck. Long postprocessing in that thread can degrade other requests. In a gaming VTuber, a 20-second research job should not delay a viewer-facing first phrase or disrupt game 1%-low FPS. STAR should maintain three QoS lanes: **motor actions** (deterministic local controller, not an LLM per keypress), **conversational speech / immediate perception** (strict latency budgets), and **strategy / knowledge / model experiments** (preemptable or deferred). The existing `AdaptiveQoS`, Linux PSI observer and `StreamBrainGovernor` are natural enforcement locations.

Do **not** blindly maximize llama.cpp `--parallel`: more slots divide finite KV/cache and can increase queueing/VRAM pressure on an 8 GB GPU. Benchmark prompt prefix reuse, context length, CPU offload and slots jointly on identical model quantization, game workload, hardware and fixed prompts. Measure request admission, first speakable phrase, physically witnessed audio/OBS output, response correctness and completed-task time. Track memory stalls and p50/p95, not just tokens per second. Try Rust only for **profiled** hot loops (e.g. capture hashing/transport), not as a rewrite of STAR's AI orchestration.

### 3. A natural VTuber needs *restraint* as much as expression

During a hard fight STAR's first duty is responsive controls and deliberate silence. A moderated question should be retained briefly and revisited as "asked earlier" only when focus returns, not treated as new breaking information. The inbox patch prevents per-event anonymous IDs defeating fairness, but source moderation remains an external requirement. No viewer message can command tools, unlock microphones or authorize game inputs.

Stage expressions should be driven by genuinely observed state plus recognized speech markers: small eye/ear focus shifts, blink timing, mouth visemes, eyebrow and head gesture, damped twin-tail hair simulation, laughter triggered by relevant events, and optional cat/puppy style overlays. Avoid arbitrary looped enthusiasm or invented "my childhood" stories. Maintain distinct memory kinds: `observed_game_event`, `audible_statement`, `hypothesis`, `creative_persona_lore`. STAR can be personable and funny while transparently AI.

**Artic** (February 13, 2026) studies region/context-aware streaming for real-time video assistants. This suggests a hypothesis for STAR: lower-cost region-of-interest HUD processing plus occasional full-scene frames may preserve important gameplay perception while using less bandwidth and CPU. Existing fingerprint/novelty gates allow an opt-in paired study; no general speed or accuracy benefit can be claimed until tested on her specific games.

## Proposed integrated proof-of-work experiment

1. **Reproduce the untrusted-identity issue:** offer two distinct moderated-looking events without `speaker_id`; neither may enter the inbox. Repeat with one stable authenticated speaker ID: the second simultaneous question must be declined, with only an HMAC pseudonym reaching the director. Run existing `tests/test_stream_focus_inbox.py` plus the new regression.
2. **Offline curriculum:** select an unknown Studio parkour or puzzle variant. Record a frozen build hash, scenario seeds and game version. Run at least 30 practice and 30 distinct holdout trials per skill; use actual Studio instrumentation for outcomes. Collect failure categories, not synthetic self-grades.
3. **Closed-loop creativity:** feed practice skill cards to a *different* game-building task, build a playable level, then independently launch, interact, win, save, reopen and validate scene geometry and animation. Holdout scenarios must stay invisible to the generation agent.
4. **Live-local streaming rehearsal only after gates pass:** instrument a controlled fake chat source, offline Studio game, engine logs, game FPS, PCM callback, independent loopback and a local OBS recording. Measure game-event-to-first-*captured* audio, AV skew, silence during critical movement, missed questions, and false/confabulated reactions. An audio callback is **not** evidence a viewer heard speech.
5. **Promotion:** create a Core Forge receipt linking model+code+game hashes, paired benchmark comparisons, regression suite and reviewer decision; keep rejected variants/rollbacks. This must work offline without GitHub, which remains an optional review/export layer.

## Explicit stop conditions

- Never permit the model, raw chat or an untrusted game to set moderation, viewer identity, critical-focus attestation, hardware-truth flags or the owner approval state.
- Do not claim intelligence improvements from more documents or completed games from scripts that merely compiled.
- Stop or defer background work when game frames, audio buffers, Linux PSI, network congestion or OBS frames show trouble; physical stream/microphone kill switches must not depend on the model.
- Never expose personal names, viewer IDs, game clips, voice recordings, keys or private skill-bank receipts in a public GitHub repository.
- An unmerged draft cannot be reported as deployed. CI on the existing stacked PR #834 was still queued at this inspection; verify the entire stack before merge.
