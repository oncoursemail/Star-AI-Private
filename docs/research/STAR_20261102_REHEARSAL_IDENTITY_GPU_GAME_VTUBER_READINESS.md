# STAR | November 2, 2026 — truthful game identity, GPU headroom, intelligence and VTuber readiness

**Status:** implementation + offline regressions for process-identity isolation; research / implementation specifications for all other items. Not a live-broadcast, voice-quality, model-training or game-mastery result. Target repository: `oncoursemail/Star-AI-Project`. Everything stays opt-in and offline-first. The trusted host, not the LLM, owns hardware measurements and permissions.

## 1. Reproduced failure and correction

In the previous `stream_windows_rehearsal_preflight.evaluate_preflight()` and `stream_windows_resource_window.evaluate_resource_window()` implementations, a perfectly stable process list containing **only OBS, VTube Studio and llama-server** could be reported as a plausible *game-ready candidate*: the caller merely pinned the llama-server PID and creation time as the alleged game. Five monotonic readings, ample fabricated VRAM and valid GPU UUID still passed. That result was a false-positive for the **existence of an independently observed game process**.

**Fixed:** one shared, case-insensitive infrastructure-process role map is now used by the one-shot preflight and sustained-window collector. OBS, avatar renderer and local-model PIDs are never valid *game* witnesses. Preflight emits `pinned_game_is_infrastructure_process`, and the sustained-window `host_processes_stable` flag now requires four *distinct* process IDs. Alias variants are regression-tested. No PID, creation time, window title, username, output path, credential, chat or model text is exported in the summaries.

**Limits:** matching a non-infrastructure PID is not proof it is a real game or the active window. OS process names can be spoofed. Before a *true Windows rehearsal*, a trusted capture host must separately pin the actual window/process, observe actual presented frames, enforce authorized input, confirm real PCM and avatar output, and enforce an authenticated OBS nonbroadcast fence. Passing the preflight never authorizes playback, gameplay or streaming.

## 2. Fresh Main-PC read-only observation

On the connected Windows computer identified as `MAIN`, read-only NVIDIA queries found a GeForce RTX 3060 Ti with **8,192 MiB VRAM, 440 MiB free, and 18% instantaneous GPU utilization** on an initial observation. A separate five-sample check (roughly 0.5 s between queries) returned **444 MiB free on every sample** with **15–18% GPU utilization**. `llama-server` was present; neither `obs64` nor `VTube Studio` appeared in the accompanying process query. These are snapshots of raw GPU counters, **not** the full pinned-GPU-UUID and process/witness stability preflight, and not a measured capacity gain or loss. There is no basis for declaring this machine *ready* for AI + gaming + avatar + OBS at once. NVIDIA documents that utilization is kernel activity over a variable sampling period, not a VRAM-availability substitute [NVIDIA nvidia-smi](https://docs.nvidia.com/deploy/nvidia-smi/index.html).

**Scheduling implication:** when visible GPU memory is near exhaustion, do not enqueue extra local GPU teachers, vision passes or image generation. Keep one fast, bounded gameplay controller and prefer CPU or a separate authorized machine for optional TTS, chat analysis, knowledge retrieval and offline practice. The reserve threshold is a measurement policy, **not** an inferred VRAM requirement of an unspecified game. Do not kill running processes just to manufacture a clean reading. A real three-phase preflight must observe idle, *game-only* and *game+OBS+avatar+speech* separately.

## 3. Better intelligence comes from measured task success, not larger prompts

Roblox **OpenGameEval**, posted October 1, 2026, evaluates 84 curated Roblox Studio tasks with actual scene and simulated-play checks. Investigating relevant objects before editing correlated with more successes; this is not evidence that any given new prompt guarantees an improvement. STAR already has `studio_inspection_coverage`, scene-integrity tools, live-input smoke tests and playtest infrastructure; use those rather than inventing a parallel harness. Run an agent against fresh tasks as `inspect -> plan -> candidate set -> sandbox/playtest -> game-state assertion -> visual/geometry audit -> repair -> independent replay`; report first-attempt pass rate, 5/5 repeatability, median total cost and held-out task performance. **Never score generated code as a successful game solely because it compiles.** [OpenGameEval paper](https://arxiv.org/abs/2610.02563), [official implementation](https://github.com/Roblox/open-game-eval), [Roblox StudioTestService](https://create.roblox.com/docs/reference/engine/classes/StudioTestService).

RealtimeBench / TORSI, published **October 14, 2026**, studies 180 time-sensitive tasks across six game families. Its key lesson is that a clever response delivered late can be a worse move than a simpler action on time. Use STAR's existing deadline router, skill bank and signed holdout gate: a **small fast actor** responds during live play, a **medium planner** acts only when safe, and an **offline teacher** studies trajectories, proposes compact reusable tactics, and must beat a frozen baseline on unseen maps before a strategy is accepted. Never confuse synthetic offline verdicts with demonstrated live winning skill. [RealtimeBench paper](https://arxiv.org/abs/2610.20665).

General knowledge: retrieve only owner-reviewed sources, include source revision and freshness, distinguish current verifiable facts from character lore, check citations against real retrieved content, and self-test with hidden answer keys maintained by the trusted host. Evaluate correctness, calibrated abstention and retrieval latency jointly. More stored text is not equivalent to more general intelligence.

## 4. Speed improvements to benchmark, not assert

1. **VRAM-aware work placement:** game rendering/OBS/Live2D first; optionally route the teacher and embeddings to a separate machine, where service health and network jitter must be measured. Synthetic 8 GB model throughput figures are not transferable to simultaneous RTX 3060 Ti gaming and streaming.
2. **Measure the real critical path:** game event observed -> decision sent -> authenticated action claimed; viewer silence -> first *audible* PCM (not the first token); audible start -> first rendered avatar frame; FPS/render gaps **during** speech. Existing modules: `inference_stream_benchmark`, `stream_rehearsal_recorder`, `stream_windows_resource_window`, `obs_nonbroadcast_rehearsal_host`.
3. **Prompt-cache experiments:** keep the stable system/tool prefix constant and vary one cache/server setting at a time. `llama-server` supports cache and slot APIs, RAM cache controls, speculative decoding and mixed-batch scenarios. Measure cold and warm p50/p95 first-visible, first-speakable, end-to-end delay, quality and host RAM occupancy under the same workload. Avoid caching private user context between unrelated viewers and never publish a raw slot snapshot. [llama.cpp server documentation](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/README.md), [SPEED-Bench](https://github.com/ggml-org/llama.cpp/blob/master/tools/server/bench/speed-bench/README.md).
4. **Adaptive vision budget:** skip redundant frames in stable scenes, prioritize changes and task-relevant regions, suspend expensive image reasoning when game FPS or free VRAM declines; only an independent host provides true timing and game-state evidence.

## 5. A genuinely convincing (but honestly AI) VTuber

**Conversation:** Stream an audible response in meaningful phrases, not one word at a time. Let an independently authenticated owner interrupt; respect actual guest speech, silence and TTS playout completion. LiveKit's `v1-mini` end-of-turn detector runs locally on CPU, so it is a candidate for an A/B test against STAR's existing host-VAD timing gate, not evidence that it is already integrated. Test on interrupt-heavy, noisy and mixed-speaker audio with **no raw viewer audio in permanent telemetry**. [LiveKit turn detection](https://docs.livekit.io/agents/logic/turns/turn-detector/).

**Voice:** Kyutai Pocket TTS v4.0.0 (**October 20**) released 18.2M, 6.9M and experimental 1.9M-parameter English variants; v4.0.1 (**October 21**) corrected short-model speech behavior. These could move some synthesis onto CPU but require tests for expressiveness, mispronunciations, laughter continuity and time-to-first-audible **on the owner hardware**. Do not infer voice quality from parameter count or marketing speed. [Pocket TTS repo](https://github.com/kyutai-labs/pocket-tts), [dated releases](https://github.com/kyutai-labs/pocket-tts/releases).

**Performance, gaze, emotion:** Map actual events to bounded reactions, and verified audio amplitude/timing to mouth motion. Natural gaze should use recent trusted scene targets rather than invented focus points; test head/eye jerk, blink and frozen-frame incidence on recorded **synthetic or consented** footage. VTube Studio plugins can inject custom animation parameters, but require explicitly granted, revocable permissions. The character may display emotions, curiosity, humor and remember verified achievements without claiming to be a real human or inventing a lived biography. [VTube Studio official plugin documentation](https://github.com/DenchiSoft/VTubeStudio/wiki/Plugins).

**Long-lived personality:** Keep a consistent fictional persona across streams, anchor reference to actual game/version/objective, separate real verified events from fictional lore, and give Astro/Amber their own turn priorities. Handle change-of-game stale speech and memories using existing scene-handoff and provenance gates before any on-air use.

## 6. Execution order and qualification gates

**P0 — host truth and capacity:** pass the regression tests here, then perform an explicit nonbroadcast Windows read-only preflight with *distinct* live OBS/avatar/model/game process identities and sustainable GPU headroom. If any component is absent, record `deferred` rather than spoofing a game. Do not start services or free GPU memory without host authorization.

**P1 — complete integrated nonbroadcast rehearsal:** pin game capture identity and actual presentation callbacks; record a bounded scene-to-action loop, real PCM heard by the output device, avatar-render frames and OBS stats across the same monotonic window. Require clean worker termination and no actual broadcast. Export numbers only. Compare the same game scene/task and hardware across baseline/candidate runs. No artificial prerecorded data may be labeled as a live host test.

**P2 — outcome-based gaming intelligence:** 20+ paired unseen trials from at least two distinct scenarios per candidate (existing gate), plus repeated controlled Roblox playtests and source-pinned general knowledge challenges. Include failure counts, FPS, action p95, and whether improvements reproduce on novel seeds; never have the same model write its own ground truth.

**P3 — humanlike streaming quality:** independently reviewed dialogue interruptions, gaze target validity, audio-to-avatar synchronization, coherent scene memory and speech prosody, tracked alongside game FPS and thermal/VRAM pressure. Establish quality targets on real hardware **after** a baseline exists; do not announce arbitrary fps/token targets as achieved.

**Not accomplished here:** no model weights changed; no real-game win rate, naturalness, TTS quality or token speed improvement was measured; no game was controlled and no OBS broadcast was started. This is one independently tested infrastructure correction and a prioritized, source-grounded design for the next integration.
