# STAR plays games: research, design, limits (2026-10-26)

Goal (owner, 10-26): STAR plays games on her own PC (RTX 4060 8 GB) in a human-like way, sees the game as fast as
she plays, and talks, laughs and coordinates with people while playing. This page: what the state of the art does,
what fits on a 4060, what was built in `star/play/`, and what it honestly cannot do yet.

Labels: **[measured]** = run on the owner's dev PC (RTX 3060 Ti, not STAR's PC) by this agent;
**[source]** = from the linked page; **[estimate]** = my reasoning, not measured.

## 1. Findings in five lines

1. Every agent that plays in real time splits the work: a fast layer that acts many times a second and a slow
   language layer that plans and talks. Neuro-sama pairs a separate game AI with an LLM persona; Lumine reasons only
   when needed; SIMA 2 picked Flash-Lite for latency. A VLM in the control loop is too slow: in VideoGameBench the
   best model finished 0.48% of the games, and latency was the main reason.
2. For Minecraft the proven path is the Mineflayer API plus a code skill library (Voyager, Mindcraft). It does not
   go through pixels at all. Voyager: 3.3x more unique items, 15.3x faster tech-tree milestones than earlier methods.
3. For games with no API (Roblox), the fast layer must be tiny: colour or YOLO-n detectors take a few ms
   ([source]: YOLO11n 1.5 ms on a T4 with TensorRT), while small VLMs take hundreds of ms (Florence-2-base 652 ms
   for 128 tokens on an L4). So VLMs give a 1-2 Hz "glance"; they are never the reflex.
4. Human-like input is known science: reaction time follows an ex-Gaussian, pointing time follows Fitts' law, and
   pointer paths are curved with a bell-shaped speed profile and corrective sub-movements. Straight constant-speed
   moves are the giveaway.
5. Skill from pixels comes from imitation (VPT, CS:GO behavioural cloning, Lumine: 1,731 h of play), not from
   prompting. A per-game policy cloned from recorded play is the route to "plays well". It needs data that STAR
   does not have yet.

## 4. Human-like input (`star/play/humanlike.py`)

- **Reaction time.** Drawn from an ex-Gaussian (a normal plus an exponential tail), the standard model for reaction
  time distributions ([Palmer et al. 2011](https://search.bwh.harvard.edu/new/pubs/RTdistPalmerEtAlJEPHPP11.pdf),
  [biorxiv](https://www.biorxiv.org/content/10.1101/2023.05.29.542684.full.pdf)). Defaults: mu 200 ms, sigma 30 ms,
  tau 60 ms, floor 130 ms. **[measured from the generator]** p50 247 ms, p95 387 ms. The delay applies only to a
  new stimulus; keeping W held costs nothing. Starting her own next job waits about two reaction times.
- **Pointing time.** Fitts' law, MT = a + b*log2(D/W+1), with a = 80 ms and b = 120 ms/bit [estimate: typical
  mouse range]. Results: 100 px to a 40 px target takes 297 ms; 800 px to a 20 px target takes 723 ms.
- **Path.** A bezier bent sideways, with a minimum-jerk speed profile (slow-fast-slow) and tremor that fades out.
  About 25% of aims overshoot by 3-9% and come back with a short corrective sub-movement. Minimum jerk alone fits
  only the first surge and misses corrections ([arXiv 2110.00443](https://arxiv.org/pdf/2110.00443)). Constant
  speed and fixed duration are the classic giveaways ([WindMouse docs](https://windmouse.readthedocs.io/en/latest/algorithm.html)).
- **Imperfection.** 4% of aims land 0.5-0.8 target widths off, held keys vary by ±12%, taps last 60-130 ms, and an
  optional slip onto a neighbouring key (off by default; a wrong key can open an inventory).
- **Purpose.** Natural play at human skill. Nothing here hides cheating: there is no aim assist, no reading of game
  memory, and no superhuman reactions (the floor is 130 ms). Input is ordinary `SendInput`, sent only while the game
  window is in front.

## 5. Design: the two-tier loop (`star/play/`)

```
 FAST, own thread, 10-30 Hz (Roblox 20 Hz, Minecraft 10 Hz)            SLOW, own thread, ~1 Hz or on a moment
 observe: frame (dxcam/BitBlt) -> ColorDetector/YOLO (+OCR 1/10)       situation: goal + controller.describe()
          or Mineflayer state event                                      + recent moments + chat (as data)
 controller.decide(obs, goal) -> intents                                 -> LLMPlanner (voice LLM / brain 1)
 act: HumanInput.plan -> Actuator thread -> SendInput (window check)     -> new goal (only from the game's list)
 moments (checkpoint, death, objective) ---------------------------->   -> optional line (max 12 words) -> speak()
        \-> voice call GameMomentWindow (star/voice/game_context.py)     speak() = the voice loop's queue: she
        \-> star.emotion events (when that module is installed)          talks on the voice thread while playing
```

- The fast loop never waits for a model. If the planner is slow or down, play continues on the current goal.
  **[measured]** With a fake planner taking 0.8 s per call on the slow thread, 20 Hz tick intervals stayed at p50
  50.0 ms and p95 50.5 ms (one 86 ms outlier) over 5 s.
- A game moment wakes the slow loop at once, so a reaction such as "nooo" can follow a death within one planner
  call instead of the next 1 s tick.
- Chat lines are wrapped as untrusted data in the planner prompt. A goal outside the game's list is rejected; a
  spoken line can still go through.
- **Minecraft.** Mineflayer's 10 Hz state stream (`skill_runner.js`) feeds the reflexes: flee when a hostile is
  within 6 blocks and health is 10 or below; eat when hungry and safe; each waits a reaction time and interrupts the
  current job. Goals name skills from her library. `learn_skill` runs the Voyager loop on a side thread: retrieve
  related skills, the model writes NAME, DESCRIPTION, EXPECT and code, a static check runs, then a timed run, then a
  mechanical check of EXPECT on before/after snapshots, then retry with feedback (3 tries). Only skills that met
  their EXPECT are verified; seed skills start unverified. Skills can call verified skills (`h.skill`), and their
  code is sent along. Skills turn the camera at human speed (`h.look`, minimum jerk) instead of snapping.
- **Roblox (one experience type: classic obby).** Colour blobs for platforms, checkpoint pads and kill bricks; the
  colours live in a per-experience `ObbyProfile`. Hold W and strafe A/D to keep the target centred; turn the camera
  with a right-drag when the target is far to the side; jump over kill bricks or when the ground ends ahead; report
  a "checkpoint" moment once per pad.

## 6. Honest capability limits

**Minecraft (Mineflayer).**
- Mineflayer is a protocol client: she plays as a real player on the server, but not through the game window. It
  works only on servers that allow bots (her own world first; `allows_bots` in social-games). Anti-bot plugins can
  kick her.
- Learned skills are only as good as the code the model writes. Voyager used GPT-4. [estimate] A 4-8B local model
  writes far fewer working skills; brain 1 is better but slower. Verification keeps broken skills out of the
  library, but it does not make the model smarter.
- Node's `vm` is not a security boundary. The static check refuses `require`, `process`, `eval`, `constructor` and
  similar names, and only her own planner writes skills. A synchronous infinite loop inside a skill freezes the bot
  process: the timeout cannot interrupt synchronous code.
- Seed skills (`collect_oak_logs`, `eat_food`, `flee_hostile`, `explore_nearby`) were tested only against a fake
  bot. None has run in a real world yet. Combat, parkour and building are weak (no PvP skill on purpose).
- `bot.js` (social-games branch) needs a two-line hook to load `skill_runner.js` (see the notes file). Until that
  lands, the Minecraft fast layer has no state stream.

**Roblox (screen + input).**
- Colour heuristics only: no depth, no jump-distance physics, no enemies or moving platforms. [estimate] Expect
  frequent falls on hard jumps. Colours must be set per experience from screenshots; the defaults are a guess.
  **Not run against a real Roblox game in this session**, so there is no success rate.
- No trained policy yet. "Plays well" in a specific experience needs recorded play (frames plus inputs) and a small
  cloned policy, as in the CS:GO and VPT work above. That is the next step, not done.
- Chat OCR needs RapidOCR (or similar) installed on her PC. dxcam and onnxruntime-gpu are not installed here.
  BitBlt capture works without them.
- Roblox's Terms restrict automated play: there is account risk (the owner accepted it on 2026-10-26).

**General.**
- No GPU model was run in this session: no detector model is on disk, and downloads were not done. GPU numbers in
  section 3 are [source] or [estimate]. Planner latency with the real voice model is [estimate]: brain 1 is busy, and
  the 4060 voice stack is not set up yet.
- Talking while playing depends on the voice loop's `speak` queue (senses-voice / star.voice). The slow loop only
  hands it lines, rate-limited to one per 6 s.
